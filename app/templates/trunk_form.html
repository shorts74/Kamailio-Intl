A trunk is one specific connection to a carrier or PBX -- its own IP, auth, and routing settings. It must belong to a SIP Profile on this node (the listener socket it's reachable through).

Asterisk-based PBX systems (including PBXact) commonly challenge with the literal realm asterisk, regardless of the trunk's actual domain -- Trust provider realm (default) handles this automatically; if you've turned it off, this is the first thing worth trying.

Caller ID Settings — Inbound
This trunk's own requirement for calls originating from it (it's the SOURCE) -- decides which number is actually used, and enforces what this trunk is allowed to claim as caller ID. The full resolution order: the number is extracted from wherever it lives on the wire (plain header, or PAI/RPID if preferred below) → this Inbound enforcement applies → routing matches/manipulates against the enforced value → the destination's own Outbound enforcement gets final say.

Access control (additional trusted source IPs)
This trunk's own IP/hostname above is always trusted regardless -- attaching an ACL here adds further trusted source IPs/CIDR ranges on top of that, for Peer trunks whose traffic can legitimately arrive from more than one address (a multi-node PBX cluster, an SBC with several egress IPs). Most relevant when Auth mode above is IP-based, since that's the only authentication a Peer trunk without Digest credentials has. Only Allow entries apply here -- Deny entries in an attached ACL have no effect on trunk source-IP trust. Multiple ACLs can be attached to the same trunk -- all of them are checked (an allow in any one is enough). Manage Access Control Lists.

Trust CIDRs (source-IP trust only -- not identity)
Different from Access Control Lists above: ACLs establish this trunk's identity (which specific trunk a call came from, feeding trunk_ip_identity). These two fields are pure trust -- a coarser "is this source even allowed to be considered at all" gate, for when the admin wants a much broader subnet trusted than identity resolution should ever use. Never populated into any identity-resolving structure, regardless of Auth mode. Digest-mode trunks only -- IP-mode trunks rely on ACL/identity exclusively, since a broader trust fallback there would defeat the purpose of IP-mode auth. Leave at 0.0.0.0/0 (trust from anywhere) to match today's default, unrestricted behavior.
